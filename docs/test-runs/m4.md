## 4. Bugs and risks

Severity scale: blocker, major, minor, cosmetic. File and line are from the working tree on 2026-11-27.

### QA04-B1 (minor): the planner can return 61 requests against a budget of 60

- **Owner:** react-native-engineer (RN-07).
- **Platform:** iOS (the iOS budget is 60; Android is 150, same logic).
- **Where:** `apps/mobile/src/features/notifications/planner.ts:383-391`.
- **Steps:** Schedule five Country loaf bakes with ready times Sat 10:00, Sat 14:00, Sun 10:00, Sun 14:00, Mon 10:00 (default heads-up 10 min, or 15 as in the tests). Read the pending `sa1:` count (in the app: `/dev-notifications` in a dev build; in tests: `budgetAndDst.test.tsx`).
- **Expected:** at most 60 (ADR 0011 section 3: "Budget: iOS 60", leaving 4 spare under the 64 cap): 59 starts and folds, the sentinel, and no more.
- **Actual:** 61, made of 44 starts, 15 folds, 1 heads-up and 1 sentinel (the test reproduces it with two 4-recipe bakes plus two single bakes, and the same count with five single bakes). The code takes `budget - 1` critical intents, then fills `budget - taken` = 1 slot with a heads-up that fires before the horizon, then appends the sentinel on top.
- **Evidence:** `budgetAndDst.test.tsx`, `it.failing('BUG: never plans more than the 60-request budget when the sentinel is needed')`. The passing test "is still under the hard 64 cap with the test reminder pending" shows the platform cap is not reached (61 plus one `satest:` is 62).
- **Impact:** low. Three spare slots remain instead of four. The risk is that a later change (a second sentinel, the ready notification flag, 2 test reminders) walks into 64 without anyone noticing.
- **Suggested fix:** reserve the sentinel's slot: when `leftOut`, use `room = budget - takenCritical.length - 1`.

### QA04-R1 (minor, unverified): a tap may stack a second copy of the live screen

- **Owner:** react-native-engineer (RN-07).
- **Where:** `apps/mobile/src/features/notifications/hooks/useNotificationTaps.ts:28` uses `router.push(...)` for every bake route.
- **Why it matters:** T-LIFE-4 expects "same destination; no duplicate screens on the stack". If the user is already on `/bake/<id>` and taps another reminder for it, `push` can add a second instance, so Back lands on the same bake again.
- **Verification:** cannot be checked with the router stand-in. Manual B4 and B5 decide it. If it stacks, use `router.navigate` (or `router.replace` when the top route is already a bake) and update `taps.test.tsx`.
- **Evidence:** code only. No test fails.

### Observations (no action needed now)

- **O1, headsUp fallback is 15, the stored default is 10.** `useScheduleSettings.ts` falls back to 15 min when the settings row has not loaded; the database default and ADR 0011 say 10. In the app, settings are hydrated behind the DB gate, so a user only sees 10. The tests that use the fallback record 15 (`bakeNotificationFlow.test.tsx` passes `headsUpMin` explicitly). Worth aligning to 10 so a hydration race cannot create a different lead.
- **O2, `cancelBakeNotifications` has no caller.** Cancel, finish and sweep use `rescheduleBake`, which diffs and works. A bake delete (softDelete) and the RN-09 restore have no seam yet: restore must call `reconcileNotifications({ mode: 'rebuild' })` (T-REB-5), and a delete path must call either.
- **O3, plan section 9 spec note stands:** `docs/design/screens-bake.md` section 3.3 still has the 18 h cold-ferment quiet-hours text wrong (the warning moves to "Mix and rest"); the code and tests are consistent with the corrected behavior (DR-02 owns the text).
- **O4, ready notification (B8):** off by default. With `flags.readyNotification` true the planner emits one `ready` per item at the end of Cool; this is unit-tested in `planner.test.ts` only, and no cross-seam test covers it. Add one when the flag is decided.
- **O5, Android `SCHEDULE_EXACT_ALARM` is not declared in `app.config.ts`** (plan section 9). Android exact alarms count as denied until it is. BLOCKED-ANDROID.
